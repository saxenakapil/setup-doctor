- 2026-09-29: Phase 5 implemented (Wrapped for Claude Code: parse-claude.ts, dedup, metrics, persona, price table, the card in all three themes and both sizes, PNG via optional dependency, `--period`/`--tz`/`--anonymize`/`--no-cost`/`--show-projects`, SKL-06/MCP-05 activated). Section 11.1 says "verify against real logs in Phase 5" — this session is itself running as Claude Code, so real logs existed on the build machine at `~/.claude/projects/`. Inspected them read-only (never displayed raw contents in chat) to ground the parser in the actual schema rather than the spec's necessarily-terse sketch. What changed from a literal reading of section 11.1:
  - **Assistant dedup is not "one line per turn."** A single logical assistant turn is split across multiple JSONL lines, one per content block (e.g. a `thinking` block and a `tool_use` block each get their own line), all sharing the same `(message.id, requestId)` pair and repeating the identical `usage` totals verbatim. On a real 2,275-line session file this collapsed 679 raw assistant lines to 405 unique pairs. The parser (`parse-claude.ts`) buffers by `(id, requestId)`, takes `usage` from the first line seen for a pair, and **merges `tool_use` names across every line sharing that pair** — a naive "dedup and keep one line" approach would silently drop most tool calls.
  - **Most `type: "user"` lines are not human input.** Claude Code represents tool-result round-trips as `role: "user"` messages (the Anthropic Messages API convention): on the same real file, 389 of 415 user-type lines were pure `tool_result` echoes and only 25 had actual `text` content one of which included the human input; a literal `type === 'user'` count for "busiest hour" would measure tool-completion timing, not human activity. The parser only yields a `kind: 'user'` record when the line's `message.content` contains at least one `type: 'text'` item; pure-`tool_result` lines are dropped entirely (not counted anywhere).
  - **SKL-06's "Skill tool call" and "`/<skill-name>` user record" both resolve to a real, observed shape.** A `tool_use` block named `Skill` carries `input: { skill: "<name>", args: "<free text>" }` (observed via real `Skill` invocations on this machine); the parser extracts only `input.skill` into `SessionRecord.tools` and never retains `input.args` (that's prompt-like free text). A user text line is checked against `^\/[A-Za-z0-9][A-Za-z0-9_:-]*` and the matched token (e.g. `setup-doctor:doctor` for a namespaced plugin skill) is pushed the same way. This heuristic has an unavoidable false-positive mode (real example seen: a sentence describing a URL path, `"/recipes/new lacks..."`, matches the regex) — accepted since rules.md's own SKL-06 spec is this simple, and the failure direction (treating a false match as "used") is the safe one for a `possible`-flagged finding.
  - **Project directory names are kept as-is, not decoded.** Claude Code encodes a project's filesystem path into its `~/.claude/projects/<encoded>` folder name by replacing `/` with `-` (confirmed: `-Users-kapil-Documents-code-setup-doctor`). This is lossy — a real path segment containing a hyphen (e.g. `hrin-app-web`) is indistinguishable from an encoded `/`. `SessionRecord.project` uses the raw encoded name verbatim as a display label; no attempt is made to reverse it, since doing so would sometimes silently invent path separators that were never there.

- 2026-09-29: Phase 8 implemented (fix mode, stretch goal). Only INS-03 (exact duplicate lines within one file) is actually reachable as a safe fix. **MCP-02's "identical duplicate entries within one file" cannot occur in this tool's model at all**: the adapter parses MCP config with `JSON.parse`, and a JS object literal cannot hold two properties with the same key -- `JSON.parse('{"a":1,"a":2}')` silently keeps only the last one. By the time the model exists, a same-file duplicate server name has already been collapsed to one entry; there is nothing left for MCP-02 to see, let alone fix. A real implementation would have to detect duplicate keys in the raw config *text* before parsing, which is a materially different (and more invasive) mechanism than "compute a diff from the Finding objects the rules already produce." Left as a backlog item rather than building a rule-specific raw-text scanner for a scenario the stretch goal only allotted a fraction of a phase to.
  - **Real bug found and fixed via end-to-end testing, not caught by unit tests alone**: after a real `--fix --yes` run, the reported "score after" was *lower* than "score before" -- for a fix that removed a finding! Root cause: `.setupdoctor-backup/<timestamp>/` (where fix mode copies pre-edit files) sat inside the project tree, and `SKIP_DIRS` (used by nested `CLAUDE.md`/`AGENTS.md` discovery) didn't exclude it. The very next `runDoctor` call (used to compute "after") found the just-created backup copy of the *original, still-duplicated* `CLAUDE.md` as a second nested instruction file and re-triggered INS-03 against it. Fixed by adding `.setupdoctor-backup` to `SKIP_DIRS` (`src/core/defaults.ts`). This is exactly the kind of bug that only surfaces by actually running the full flow against real files and checking the *numbers*, not just that a message was printed -- the original CLI test only asserted `text.toContain('Score after:')`, which passed even with the wrong number in it; strengthened to assert the literal `Score before: 95   Score after: 100` string, and added a fixture-independent regression test directly on `findNestedFiles`'s `SKIP_DIRS` handling (`test/adapters/fs-utils.test.ts`).
  - **Second real bug, caught by CI's Windows runners specifically**: `fix.ts` read the target file fresh via `readTextFileSafe` (correctly, since the file may have changed since discovery) but never normalized `\r\n` to `\n` the way every adapter does at discovery time. On a CRLF checkout (git on Windows commonly defaults `core.autocrlf=true`), the finding's line numbers were computed against LF-normalized text but applied to raw CRLF text, leaving stray `\r` characters in the "fixed" content and failing exact-match assertions. Fixed two ways: `fix.ts` now normalizes `\r\n` to `\n` on read, matching every other file-reading path in the codebase; and added a repo-root `.gitattributes` (`* text=auto eol=lf`) so every fixture checks out with LF on every platform going forward, not just this one file. Added a CRLF-specific unit test (`test/core/fix.test.ts`) that writes `\r\n` content directly, so this is caught locally on any OS, not only by waiting for a Windows CI run.

## Backlog / v1.1+ ideas

Not in v1 scope. Recorded so Phase 1 to 8 decisions do not foreclose them.

- **Score history and regression detection.** A local, opt-in, no-network `.setupdoctor-history.jsonl` appended on `--ci` runs, so a future `--compare` flag or CI action can flag "score dropped since last run." Low retrofit cost since JSON output already carries `schemaVersion`; no architecture change needed now.
- **More agent adapters.** GitHub Copilot instructions (`.github/copilot-instructions.md`), Windsurf, Cline, Continue.dev. The `Adapter` interface is already generic; adding one is a new file, not a core change.
- **Deeper settings and hooks coverage.** Beyond SET-01/SET-02: hooks that shell out to network tools, deny-lists so broad they block legitimate work, hook commands that could leak env vars into logs. Each is a new rule (spec, fixtures, tests), so treat as incremental v1.1 additions, not a v1 gap.
- **Fix mode expansion beyond the Phase 8 safe set.** MCP-02's own "same file" case is unreachable as described (see the Phase 8 decision above) -- if it's still wanted, the real work is a raw-text duplicate-JSON-key scanner run before `JSON.parse`, not a rule tweak. Other candidates: FRS-02 (swap retired model name), SKL-02 (rewrap an out-of-range description), MCP-04 (disable least-used server). Only add after each proves safe and mechanical, per section 14.
- **Wrapped trend and comparison view.** "This week vs last week" on the card or terminal report. Secondary to Doctor's core value; also, subagent invocations will already surface in the existing "top tools" metric once section 8.1's `kind: 'agent'` modeling lands, so this is lower urgency than first thought.
- **Codex/Cursor Wrapped via SQLite.** Both `~/.codex` (`logs_2.sqlite`, `state_5.sqlite`, ...) and `~/.cursor/ai-tracking/ai-code-tracking.db` exist and plausibly hold usable usage data, but their schemas are completely undocumented and specific to internal app versions -- a real reverse-engineering project, not a "verify against real logs" afternoon like Claude's JSONL turned out to be. Worth revisiting only if there's a documented schema (from the vendor or a well-maintained community project) to build against, since an undocumented SQLite schema is exactly the kind of dependency that silently breaks on the next app update.
