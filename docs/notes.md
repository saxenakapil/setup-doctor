- 2026-09-29: Phase 5 implemented (Wrapped for Claude Code: parse-claude.ts, dedup, metrics, persona, price table, the card in all three themes and both sizes, PNG via optional dependency, `--period`/`--tz`/`--anonymize`/`--no-cost`/`--show-projects`, SKL-06/MCP-05 activated). Section 11.1 says "verify against real logs in Phase 5" -- this session is itself running as Claude Code, so real logs existed on the build machine at `~/.claude/projects/`. Inspected them read-only (never displayed raw contents in chat) to ground the parser in the actual schema rather than the spec's necessarily-terse sketch. What changed from a literal reading of section 11.1:
  - **Assistant dedup is not "one line per turn."** A single logical assistant turn is split across multiple JSONL lines, one per content block (e.g. a `thinking` block and a `tool_use` block each get their own line), all sharing the same `(message.id, requestId)` pair and repeating the identical `usage` totals verbatim. On a real 2,275-line session file this collapsed 679 raw assistant lines to 405 unique pairs. The parser (`parse-claude.ts`) buffers by `(id, requestId)`, takes `usage` from the first line seen for a pair, and **merges `tool_use` names across every line sharing that pair** -- a naive "dedup and keep one line" approach would silently drop most tool calls.
  - **Most `type: "user"` lines are not human input.** Claude Code represents tool-result round-trips as `role: "user"` messages (the Anthropic Messages API convention): on the same real file, 389 of 415 user-type lines were pure `tool_result` echoes and only 25 had actual `text` content one of which included the human input; a literal `type === 'user'` count for "busiest hour" would measure tool-completion timing, not human activity. The parser only yields a `kind: 'user'` record when the line's `message.content` contains at least one `type: 'text'` item; pure-`tool_result` lines are dropped entirely (not counted anywhere).
  - **SKL-06's "Skill tool call" and "`/<skill-name>` user record" both resolve to a real, observed shape.** A `tool_use` block named `Skill` carries `input: { skill: "<name>", args: "<free text>" }` (observed via real `Skill` invocations on this machine); the parser extracts only `input.skill` into `SessionRecord.tools` and never retains `input.args` (that's prompt-like free text). A user text line is checked against `^\/[A-Za-z0-9][A-Za-z0-9_:-]*` and the matched token (e.g. `setup-doctor:doctor` for a namespaced plugin skill) is pushed the same way. This heuristic has an unavoidable false-positive mode (real example seen: a sentence describing a URL path, `"/recipes/new lacks..."`, matches the regex) -- accepted since rules.md's own SKL-06 spec is this simple, and the failure direction (treating a false match as "used") is the safe one for a `possible`-flagged finding.
  - **Project directory names are kept as-is, not decoded.** Claude Code encodes a project's filesystem path into its `~/.claude/projects/<encoded>` folder name by replacing `/` with `-` (confirmed: `-Users-kapil-Documents-code-setup-doctor`). This is lossy -- a real path segment containing a hyphen (e.g. `hrin-app-web`) is indistinguishable from an encoded `/`. `SessionRecord.project` uses the raw encoded name verbatim as a display label; no attempt is made to reverse it, since doing so would sometimes silently invent path separators that were never there.

- 2026-09-29: Phase 8 implemented (fix mode, stretch goal). Only INS-03 (exact duplicate lines within one file) is actually reachable as a safe fix. **MCP-02's "identical duplicate entries within one file" cannot occur in this tool's model at all**: the adapter parses MCP config with `JSON.parse`, and a JS object literal cannot hold two properties with the same key -- `JSON.parse('{"a":1,"a":2}')` silently keeps only the last one. - 2026-09-29: Phase 16 (post-v1): Wrapped trend/comparison view (`--trend`). The concern flagged when this was first put on the backlog -- "needs to be built agent-aware from the start" because Cursor Wrapped has a narrower metric set than Claude Code/Codex/Copilot (no per-message busiest-hour granularity) -- turned out not to require any agent-specific branching at all, once the actual metric selection was thought through: trend only ever compares sessions, active days, tokens and cost, none of which Cursor computes any differently from the other three agents. Busiest hour/weekday were never candidates for a "delta" display regardless of agent (a point-in-time fact, like "10:00", has no meaningful "change since last period" the way a count does), so the one metric Cursor genuinely computes more coarsely was already excluded from trend for every agent, not specifically worked around for Cursor.
  - **No new history file, unlike `doctor --compare`'s `.setupdoctor-history.jsonl`.** Wrapped already has a complete historical record on disk (the session logs themselves); the "previous period" is just a second window read from the same source, not something that needs persisting between runs. This is architecturally simpler than Doctor's score-history feature, which genuinely needed a new file because Doctor has no equivalent historical record.
  - **"Previous period" is computed generically for every period kind** (`previousPeriodBounds` in `src/wrapped/run.ts`): the window of the exact same duration immediately preceding the current one's bounds. This works uniformly for `7d`/`30d`/`ytd`/an explicit range without special-casing any of them; only `all` has no meaningful predecessor (it already covers every record on disk), so `--trend --period all` returns `trend: null` with an explanation, not an error. One real, documented reading choice: for `ytd`, "previous period" is the same *number of days* immediately before January 1st (reaching back into the prior year), not "the same calendar days last year" -- simpler to compute and to reason about correctly, and honestly documented as that specific reading rather than guessing at a more "intuitive" year-over-year comparison that could be wrong.
  - **One adapter read, not two.** `Adapter.readSessions` only accepts a `Period`, not raw millisecond bounds, and `Period`'s `range` kind is day-aligned (local midnight to local midnight) while `7d`/`30d` bounds are exact-millisecond rolling windows -- mixing the two directly would have meant either a lossy day-rounded comparison or two separate reads. Resolved by fetching once, using a `range` `Period` widened by a day on each side of the combined current+previous window (cheap: an extra day of records to filter, never a correctness issue) as the fetch boundary, then classifying every record into "current" or "previous" using the exact millisecond bounds computed directly from `resolvePeriodBounds`, not from the padded fetch window. The trend delta itself is therefore exact-millisecond precise even though the underlying fetch call is day-rounded.
  - **The shareable card does not gain a visual trend element.** Card layout across three themes and two sizes is already a fixed, tightly-designed space (docs/themes.md); adding a new stat row or delta annotation to all six variants would have been the single biggest risk in this phase's original 8-12h estimate.   - **`WrappedMetrics`'s repeated `tokens.input + tokens.output + tokens.cacheRead + tokens.cacheWrite` sum** (previously written out at three separate call sites -- `cli.ts`'s card input, `terminal-wrapped.ts`'s headline, and now the new trend delta) was pulled into one exported `totalTokens()` helper in `metrics.ts` and all three sites now use it; a small, opportunistic cleanup while touching this code, not a new feature.
